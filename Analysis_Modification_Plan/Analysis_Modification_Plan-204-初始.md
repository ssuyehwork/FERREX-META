# 全局架构专业化评估与解耦规划 —— Analysis_Modification_Plan-204.md

## 1. 任务背景
在 FERREX-META 磁盘索引与视图管理工具的项目演进中，早期设计缺乏统一的顶层规划，导致大量“临时解决方案”（如跨层状态污染、高开销数据高频共享、不合理的锁竞争等）被引入。尤其在面对千万级文件检索、海量缩略图高频缩放、磁盘 I/O 实时监听等工业级业务场景时，既有代码暴露出调用链冗长、视图渲染层与后台数据控制层职责不清、线程池析构死等、UI 线程微卡顿或假死等深层次架构性缺陷。

为了彻底扭转既有系统的“临时拼凑感”，本方案通过专业软件架构设计理论，对项目底层及表现层进行全面、深度的架构审计，并给出一套极具工程专业度、开箱即用、具备高度可扩展性与高内聚低耦合性质的工业级重构与解耦蓝图。

---

## 2. 问题定位与硬伤审计
通过深度审计 `src/` 重构版中各核心模块的交互模式与物理实现，定位到如下关键架构硬伤：

### 2.1 物理边界模糊（视图层与数据控制层重度耦合）
* **病因**：`ScanTableModel` 和组件在渲染单元时，频繁调用 `MftReader::instance().getFullPath()`、`MftReader::instance().getSize()` 甚至在 `data()` 中触发 `requestMetadata` 逻辑（虽是异步，但会申请 `MftReader.m_dataLock` 锁）。
* **后果**：
  1. 在百万级数据下，当用户高频滚动列表或切换视图时，UI 主线程在渲染循环中不可避免地与后台 MFT 解析线程竞争同一把读写锁（`m_dataLock`），直接导致渲染被挂起。
  2. 视图组件依赖过多的底层实体数据，使得视图组件无法脱离 MftReader 独立进行单元测试，严重损害了**分层原则（Separation of Concerns）**。

### 2.2 状态泄露与生命周期混杂（ResultSet 的中介职责错配）
* **病因**：`ResultSet` 承载了查询出来的 `keys` (FRN)，却又混合了 `metadata`（包含 `RenderMeta` 的颜色等）。甚至曾有逻辑在后台搜索线程同步拼装特定渲染专用的属性。
* **后果**：
  1. 底层引擎（`MftReader`）在检索数据时，不得不感知前台显示专属的 UI 颜色或样式属性，违反了**高内聚低耦合（High Cohesion, Low Coupling）**。
  2. 混合状态增加了 `ResultSet` 生命周期维护的复杂性，在多线程高频增量同步（如 USN 批处理）时容易出现缓存不一致或悬空指针。

### 2.3 临时方案泛滥与事件链条混乱（高频变焦与配置写入）
* **病因**：在滑块 `QSlider::valueChanged` 或 `Ctrl+滚轮` 控制缩略图尺寸变焦时，代码中包含对 `m_config.save()` 的高频同步、阻塞调用，以及对 `clearThumbCache(true)` 的不当重设。
* **后果**：
  1. 物理磁盘写入操作被拉入高频交互事件回调中，严重阻塞 UI 主线程。
  2. 析构时，模型死等后台缩略图提取线程池（`m_thumbPool->waitForDone()`）导致关闭窗口存在秒级滞后或无响应。

## 4. 详细解决方案

### 4.1 物理分层解耦蓝图
通过重组系统架构，建立三层金字塔架构体系（数据层 - 数据控制/代理层 - 视图表现层）：

```
+-------------------------------------------------------------+
|                     视图表现层 (Presentation)               |
|  - ScanDialog (窗口中控)                                    |
|  - ListResultView / GridResultView / JustifiedResultView     |
|  - ToolTipOverlay & ThumbnailDelegate (前台修饰与绘制)        |
+-------------------------------------------------------------+
                              | (通过 View-Model 驱动)
                              v
+-------------------------------------------------------------+
|                     数据控制/代理层 (Controller/ViewModel)  |
|  - ScanController (统筹状态: FilterState, SearchText)        |
|  - ScanTableModel (轻量级数据代理, 零底层计算)               |
|  - ThumbnailWarmupPipeline (后台预热通道)                   |
+-------------------------------------------------------------+
                              | (快照隔离、无锁 SoA 投影驱动)
                              v
+-------------------------------------------------------------+
|                     核心数据/引擎层 (Core & Infrastructure) |
|  - MftReader (MFT 物理扫描、SoA 数据存储)                   |
|  - UsnWatcher (实时 USN 监听)                               |
|  - MetadataManager / CacheManager (元数据物理载体)           |
+-------------------------------------------------------------+
```

### 4.2 数据层与视图表现层代理隔离
为规避 UI 线程由于 `m_dataLock` 读写锁竞争引起的微卡顿，必须实行 **数据代理与 SoA 快照投影（SoA Snapshot Projection）模式**。

* **核心思想**：
  1. `ScanController` 在执行搜索与排序后，向 `ScanTableModel` 提供一个独立的、完全静态的、脱离底层原始 SoA 锁约束的结构（`ResultSet`）。
  2. 建立结构体的拷贝或局部投影拷贝机制。对于排序，在后台线程中将要比较的 key 对应的字段值一次性提取并存储在临时的 `SortProxy` 中进行本地排序，完全不再调用 MftReader 方法。
  3. `ScanTableModel::data()` 尽可能只进行 O(1) 的局部映射查询或基于 `thread_local` 的行内计算缓存（如 `cachedPath`），消除在同一行的不同列（如名称列、路径列、ToolTip）之间重复进行复杂的递归路径查询。

### 4.3 新设计下的统一数据流与调用链
在进行“搜索/筛选”和“缩放变焦”操作时，调用链必须实现单向闭环，无循环反馈。

#### A. 搜索与筛选数据流
```
[用户输入/分类切换] 
      │
      ▼
[ScanDialog] ──修改状态──> [ScanController]
                                 │
                                 ▼ (发起异步 QFuture)
                         [MftReader (物理检索)]
                                 │
                                 ▼ (引擎返回 keys 集合)
                         [ScanController (封装 ResultSet 投影)]
                                 │
                     (发射 resultsSwapped 快照信号)
                                 ▼
                         [ScanTableModel] ──通知视图变化──> [QAbstractItemView]
```

#### B. 变焦缩放与多级缓存流
为实现“行云流水般丝滑”的变焦：
```
[Ctrl+滚轮 / 滑块调整] ──修改 sliderValue──> [ScanDialog (IconSize 更新)]
                                                   │
                                                   ├─(防抖 200ms QTimer)──> [磁盘写入 (Config.save)]
                                                   │
                                                   ▼ (即时更新 Viewports 大小尺寸)
                                            [ScanTableModel] (清开 L1 精确缓存, 保留 L2 历史 LRU 缓存)
                                                   │
                                                   ▼ (主线程 data 优先使用 L2 平滑拉伸展示)
                                            [ThumbnailDelegate (零延迟瞬间拉伸绘制，不闪白卡片)]
                                                   │
                                                   ▼ (异步拉取新尺寸大图任务入队)
                                            [m_thumbPool (并发/串行智能调度提取)]
                                                   │
                                                   ▼ (提取成功, 注册至 L1 与 L2 并通知 dataChanged)
                                            [QAbstractItemView (高画质大图无缝替换)]
```

### 4.4 可插拔式接口设计（数据源与表现层）
* **视图表现层接口**：
  所有的具体渲染视图（如 `ListResultView`、`JustifiedResultView`、`GridResultView`）必须实现统一的抽象接口 `IScanResultView`。其内部只包含视口控制、基础滚动和布局更新方法。
* **数据存储解耦**：
  `ScanController` 不再与 `MftReader` 强绑定。通过建立类似 `IDataQueryEngine` 的抽象层，未来不管是使用当前的 NTFS 解析引擎、SQLite 数据库引擎、抑或是局域网检索引擎，均可以通过实现 `IDataQueryEngine` 来达到对 `ScanController` 与 `ScanTableModel` 的零侵入替换。

### 4.5 并行线程池隔离与零假死析构机制
* **物理隔离线程池**：
  1. **后台系统级任务**：如 MFT 初始化、全量索引检索、全量排序由全局 `QThreadPool::globalInstance()` 承载，优先级中等。
  2. **前台高频缩略图任务**：由 `ScanTableModel` 独占的隔离线程池 `m_thumbPool` 调度，优先级为低。对于固态硬盘（SSD），其并发上限设置为逻辑核心数的一半；对于机械硬盘（HDD），其并发数强制硬锁为 1，完全阻断高频无序寻道对磁盘效率的摧毁。
* **零假死析构控制**：
  在 `ScanTableModel` 析构时，彻底改变“死等”策略。
  1. `m_isDestroying` 原子变量立刻置为 `true`。
  2. 调用 `m_thumbPool->clear()` 瞬间丢弃并清空尚未开始运行的所有队列任务。
  3. 通过局部辅助静态销毁机制（如将 Pool 的释放打包并交由 globalInstance 异步去销毁释放），使 UI 主线程在用户关闭窗口时达到毫秒级瞬间响应。

### 4.6 团队协作与物理文件夹边界
为使得架构极简并便于新成员快速接手，系统在物理文件划分上实现职责一目了然的边界：
1. `src/core/`：系统生命周控（CoreController）及底层的配置载体。
2. `src/mft/`：磁盘原生驱动，处理 MFT 解析、高速位读写及 USN 高速实时监听。
3. `src/meta/`：纯粹的文件元数据标签与颜色属性存储、加载层（MetadataManager）。
4. `src/ui/`：表现层、控制器与各种 ResultView，遵循严格的 Model-View 模式协作。

## 6. 实现准则与预警【核心】

1. **头文件及依赖管理**：
   在后续进行上述解耦落地重构时，数据层的头文件（如 `MftReader.h`）绝对不能包含 `ui/` 层组件或 QWidget 相关的头文件。
2. **信号槽跨线程调用安全**：
   在 `ScanController` 与 `MftReader` 的通信中，任何由于磁盘 I/O 变化引起的 USN 信号，必须采用 Qt 默认的 `Qt::QueuedConnection` 跨线程分发，绝不能在后台 USN 线程中直接操纵 `ScanTableModel` 中的 `QList` 容器。
3. **内存控制预警**：
   `m_lastPixmapCache`（L2 历史大图缓存）虽然提供了极为丝滑的变焦，但如果不设容量上限，在百万级结果的高频缩放中会导致系统内存溢出。物理重构落地时必须显式调用 `m_lastPixmapCache.setMaxCost(200)` 来严格控制内存占用。
