# 修复 bin+idx 增量存储中的 O(n) 开销与健壮性缺口 —— Analysis_Modification_Plan-139.md

## 1. 任务背景
在现有的 `bin+idx` 缓存系统中，`appendEntries` 操作存在非增量式的 $O(n)$ 磁盘读取开销，且加载路径由于随机寻址导致性能低下。此外，记录格式缺乏完整性校验及边界保护，存在崩溃恢复风险。本次方案旨在通过重构校验机制与加载策略，实现真正的增量追加、流式加载及鲁棒的文件损坏感知。

## 2. 问题定位
- **问题一（追加开销）**：`ScchCache::appendEntries` 在每次追加增量索引后，都会执行 `ReadFile` 将历史全部索引重算 CRC（对应代码约 206 行）。这使得追加开销随记录总数线性增长，违反了增量存储的初衷。
- **问题二（数据校验缺失）**：`ScchRecord` 结构体仅包含基础元数据，缺少单条记录级别的 CRC 校验（对应头文件约 42 行）。加载时对 `name_len` 缺乏边界检查，直接执行 `resize` 存在内存溢出风险（对应代码约 255 行）。
- **问题三（随机寻址低效）**：`load()` 过程使用 `std::map<frn, offset>` 遍历，导致 `fseek` 在磁盘物理位置上频繁往返跳跃（对应代码约 247 行），在大数据量下加载速度甚至慢于全量顺序扫描。

## 4. 详细解决方案

### 4.1 数据结构调整 (ScchCache.h)
- 在 `ScchRecord` 结构体末尾（`name_len` 之后）增加 `uint32_t record_crc32;`。
- 更新 `SCCH_VERSION_MINOR` 以标识格式变动。

### 4.2 序列化与追加优化 (ScchCache.cpp)
- **`serializeRecord` 增强**：
  - 计算除 `record_crc32` 自身外所有字段的 CRC（包括 `name` 字符串内容）。
  - 将结果存入 `rec->record_crc32`。
- **`appendEntries` 减负**：
  - **采用方案 A**：删除读取历史索引计算全局 CRC 的逻辑。
  - 将 `ScchIdxHeader::crc32` 置为 `0` 或特定常数，或仅保留对主索引（Main Index）的单次校验，增量部分不再维护聚合 CRC。

### 4.3 加载路径性能与健壮性优化 (ScchCache.cpp)
- **边界检查逻辑**：
  - 在 `fread` 读取 `ScchRecord` 之后，计算当前位置到文件末尾的剩余字节数。
  - 若 `rec.name_len > 剩余字节数` 或 `rec.name_len > 1024 * 2` (文件名最大阈值)，立即报错并触发降级。
- **校验逻辑**：
  - 重新计算当前记录的 CRC 并与 `rec.record_crc32` 比对。若不符，立即停止索引加载，降级至全量扫描。
- **顺序读取改造**：
  - 废弃直接遍历 `std::map<uint64_t, uint64_t>`。
  - 将所有从 `.idx` 读取的 `ScchIndexEntry` 放入 `std::vector`，并使用 `std::sort` 按照 `offset` 从小到大排序。
  - 顺序遍历排序后的 vector 访问磁盘，确保磁头仅单向顺序移动。

## 6. 实现准则与预警【核心】
1. **CRC 计算范围**：必须确保 `record_crc32` 覆盖了 `name_len` 指向的文件名 Buffer，以防文件名截断损坏。
2. **IO 句柄安全**：在加载路径降级时，必须确保先关闭索引加载相关的 `FILE*` 句柄，再进入全量扫描逻辑。
3. **性能对齐**：按 `offset` 排序后的顺序读取必须配合单次 `fread`（而非多次 `fgetc`），以充分利用 OS 的预读缓存。

## 8. 待确认事项
1. **降级颗粒度**：当某条增量记录 CRC 失败时，是仅跳过该记录，还是立即放弃整个索引加载分支并降级为全量扫描？（建议：为了绝对健壮性，一旦 CRC 不匹配应立即视为索引已脏，触发全量重建）
2. **文件名长度上限**：`name_len` 的边界检查阈值，除了文件物理剩余大小外，是否需要设置一个逻辑上限（如 `MAX_PATH * 4` 字节）以防 OOM？
3. **CRC32 性能**：在大规模顺序加载时，单条记录 CRC 计算是否会成为瓶颈？（建议：由于磁盘 I/O 仍是慢速环节，CPU 计算 CRC 的开销在顺序读取下通常可忽略不计）
4. **Header 状态标记**：在采用方案 A 废除全局 CRC 后，`ScchIdxHeader::crc32` 字段是否应填入特定魔数（如 `0xDEADDATA`）以标识该版本索引不再受全局 CRC 保护？
5. **空文件处理**：对于全新的、尚无索引的盘符，首次生成的 `Main Index` 是否仍需一次性 CRC 校验？（建议：方案 A 应统一化，即使是 Main Index 也主要依赖单条 Record 校验）
