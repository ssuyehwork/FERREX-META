# Analysis_Modification_Plan-154.md - FERREX-META 假死与卡顿深度审计报告

## 1. 核心问题定义
当前 FERREX-META 版本在百万级数据（约 220 万项）下，输入关键字或扩展名进行筛选时，频繁出现 UI 线程假死（无响应）和明显的视觉卡顿。

## 2. 逻辑架构缺陷审计

### 2.1 读写锁饥饿与 UI 线程锁死 (Lock Contention)
- **缺陷位置**：`MftReader::search` 与 `ScanTableModel::data`。
- **傻逼逻辑**：`MftReader` 使用了 `QReadWriteLock` 保护数据。由于后台搜索任务持有读锁时间过长（百万级遍历），且 Windows 读写锁通常为“写者优先”，一旦 USN 监控线程请求写锁更新数据，后续所有 UI 线程的读请求将被无限期挂起。
- **后果**：UI 线程因为无法获取文件名用于渲染，直接进入系统层面的“无响应”状态。

### 2.2 搜索任务不可取消产生的“线程洪流”
- **缺陷位置**：`MftReader::search` 内部的 `blockingMap` 循环。
- **傻逼逻辑**：搜索循环内部没有检查 `QFuture::isCanceled()`。当用户快速输入字符时，旧的搜索任务虽然被 UI 废弃，但其底层线程依然在跑完 200 万次循环。
- **后果**：CPU 资源被无效任务占满，且每个无效任务都在参与锁竞争，形成连锁崩溃。

### 2.3 重型结果集构建成本 (Heap Churn)
- **缺陷位置**：`ScanController::updateKeyToPosMapping`。
- **傻逼逻辑**：搜索完成后，代码会在后台线程构建一个包含数百万项的 `unordered_map`。
- **后果**：海量的小内存申请导致系统频繁触发内存整理（Memory Churn），在快速输入场景下，内存带宽被哈希桶的分配耗尽。

### 2.4 字符串对象的昂贵搬运 (String Copying)
- **缺陷位置**：`MftReader::matchEntry`。
- **傻逼逻辑**：在核心搜索循环中频繁调用 `QString::fromUtf8` 或 `toStdString`。
- **后果**：在 200 万次循环中产生 200 万个临时对象，性能开销相较于裸指针对比（如 `StrStrIA`）高出 2-3 个数量级。

### 2.5 视图模型的刷新风暴
- **缺陷位置**：`ScanController` 的信号分发逻辑。
- **傻逼逻辑**：`resultsSwapped` 和 `searchFinished` 两个信号往往同时触发，导致 `ScanTableModel` 连续执行两次 `beginResetModel`。
- **后果**：TableView 强制重算所有可见行高度和布局，造成视觉闪烁和操作断档。

### 2.6 渲染管线的“锁震荡”与动态拼接
- **缺陷位置**：`ScanTableModel::data` 与 `MftReader::getFullPath`。
- **傻逼逻辑**：UI 线程渲染每一行格子时都会触发 `MftReader` 的读锁申请。同时，路径列在显示时才进行递归回溯拼接。
- **后果**：每帧重绘涉及数百次锁竞争与海量临时 `QString` 构造，导致滑动掉帧严重，性能远输于 ArcMeta 的预格式化投影方案。

### 2.7 数据库存储的“双轨制”开销
- **架构审计**：系统采用 SQLite 处理元数据，自研 SCCH (Binary) 处理 MFT 索引。
- **潜在逻辑缺陷**：在渲染阶段，UI 线程同步请求 SQLite（通过 `getMeta`）来获取文件的颜色和标签。
- **后果**：SQLite 的并发处理能力在百万级查询下会成为渲染瓶颈。应将元数据 SoA 镜像化，实现与 MFT 索引同级别的内存查表性能。

## 3. 架构优化建议 (Plan-155 预研)
1. **无锁快照化**：搜索任务应在数据快照上运行，彻底解耦 UI 渲染与数据更新。
2. **原子中断**：在搜索循环的关键路径加入取消标记检查。
3. **视图快照投影 (View Projection)**：搜索完成后预先格式化文字与元数据，UI 线程渲染时仅执行“无锁查表”，彻底消除渲染时的逻辑计算。
4. **分段交付渲染**：首屏数据优先渲染，后续数据增量更新，消除 `beginResetModel` 的主线程阻塞。
