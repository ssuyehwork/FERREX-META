# MftReader 核心架构重构（去锁化搜索与 USN 补全流水线） —— Analysis_Modification_Plan-140.md

## 1. 任务背景
在对 `MftReader` 及其扫描逻辑的深度审计中，识别出三处严重的“傻逼逻辑架构”：搜索逻辑中的锁竞争导致伪并行、USN 处理流程中的同步磁盘 I/O 阻塞主干道、以及路径回溯缺乏原子性快照。这些设计缺陷导致了系统在高负载下的界面卡顿、搜索效率衰减以及实时监听稳定性隐患。本次重构旨在通过“读写分离”与“异步流水线”思想彻底消除这些瓶颈。

## 2. 问题定位
- **架构缺陷一（搜索锁竞争）**：在 `MftReader::search` 的并行分块逻辑中（约 638 行），每 4096 项就会触发一次 `QReadLocker` 申请。在大数据量下，并行线程会频繁与 USN 写入线程争抢全局 `m_dataLock`，导致写线程被“饿死”或 UI 读操作被写操作挂起。
- **架构缺陷二（USN 同步 I/O）**：在 `updateEntryFromUsn` 这一关键路径上（约 715 行），直接调用 `OpenFileById` 获取文件大小和属性。这会导致 USN 监听线程在处理大量变动信号时发生严重阻塞，极易引发 NTFS Journal 溢出导致丢失变动感知。
- **架构缺陷三（路径回溯性能）**：`getPathFast` 缺乏对 SoA 结构的原子快照支持，且在高频并发调用下存在重复计算与缓存锁竞争。

## 4. 详细解决方案

### 4.1 搜索架构去锁化重构 (MftReader.cpp)
- **重构 `search` 逻辑**：
  - 在进入并行搜索前，**仅申请一次全局读锁**。
  - 在持有锁期间，快速获取 `m_frns.size()` 并检查 `m_isInitialized`。
  - 如果可能，允许在分块内部持有锁，但大幅调高 `grainSize`（如从 4096 调至 100000），或者通过“逻辑分块 + 单次锁保护数据视图”的方式，避免在热点循环中频繁申请/释放 QReadWriteLock。
  - **核心目标**：减少锁申请频次，将锁竞争从 $O(N/4096)$ 降低到 $O(1)$ 或 $O(N/100000)$。

### 4.2 USN 补全流水线化 (MftReader.cpp)
- **改造 `updateEntryFromUsn`**：
  - 彻底移除函数体内的 `OpenFileById` 和 `GetFileInformationByHandle` 同步调用。
  - 当监听到新增/更新信号时，仅通过 USN Record 提取 FRN、ParentFRN、文件名、属性以及 USN 本身自带的时间戳。
  - 在完成 `m_frns` 等内存登记（Status 0）后，**立即通过 `requestMetadata(finalIdx)` 将物理大小的获取排入异步任务队列**。
  - **核心目标**：使 USN 监听线程回归“零 I/O”纯计算状态，确保每秒万级记录的极速吞吐。

### 4.3 物理补全队列优化 (MftReader.cpp)
- **增强 `requestMetadata`**：
  - 引入一个带限流功能的 `QThreadPool`，专门处理文件物理属性的补全。
  - 针对 `updateEntryFromUsn` 产生的高频请求，采用合并更新策略（Debounce），避免对磁盘进行地毯式随机寻址。

## 6. 实现准则与预警【核心】
1. **死锁预警**：在 `requestMetadata` 中异步回调 UI 信号 `dataChanged` 时，必须确保不持有任何写锁，防止信号槽同步触发导致的死锁。
2. **内存一致性**：由于 USN 信号不再同步获取文件大小，UI 层在显示刚创建的文件时，大小可能暂时显示为 0，直至补全任务完成。需在 `ModelContract` 或相关代理中处理此类中间态显示逻辑。
3. **性能平衡**：搜索时单次锁持有的时间不宜过长，若记录达到千万级，建议采用“短间隔锁”或物理快照技术以兼顾 UI 响应。
