# 百万级数据量下 UI 假死与极致性能重构方案 —— Analysis_Modification_Plan-146.md

## 1. 任务背景
在 221 万项数据规模下，用户反馈筛选和扫描会导致程序“未响应”。经审计，系统在处理高频变动时，于 UI 线程执行了 $O(N \log N)$ 的全量排序，且在持有排他写锁期间执行了耗时计算。

## 2. 问题定位
- **地雷 A：主线程同步排序**
  - `ScanController::processBatchUpdates` 在 UI 线程直接执行 `std::sort`，百万级条目的排序开销超出了主线程的响应阈值（16ms）。
- **地雷 B：排他写锁内的计算堆叠**
  - `MftReader::buildIndex` 在持有 `QWriteLocker` 时执行 `std::sort`，物理阻塞了 UI 线程的所有读取请求。
- **地雷 C：搜索链路的内存分配抖动**
  - `matchEntry` 内部高频产生临时 `QByteArray` 对象，导致 CPU 核心浪费在内存管理而非业务逻辑。

## 4. 详细解决方案

### 4.1 异步双缓冲投影排序 (ScanController.cpp)
为了彻底消除主线程阻塞，排序逻辑将从 UI 线程物理剥离：
- **投影拷贝 (Projection Copy)**：在排序前，仅申请微秒级的读锁，将排序所需的“键值对”拷贝到本地副本（`std::vector<SortProxy>`）。
- **锁外计算**：在子线程执行 `std::sort`。排序过程中不触碰 `MftReader` 或 `ScanController` 的任何锁，确保 UI 线程可以自由读取数据进行列表渲染。
- **原子交换**：排序完成后，通过 `emit resultsSwapped` 异步通知 UI 线程更新模型视图。

### 4.2 写锁最小化与指针交换 (MftReader.cpp)
重构 `MftReader` 的索引更新机制：
- **方案**：将 `m_sorted_indices` 改为指针管理（或原子共享指针）。
- **实现**：新的排序结果在本地计算完毕后，通过 `std::atomic_exchange` 进行更新。
- **效果**：将原本数秒的写锁占用时间降至微秒级（指针赋值）。

### 4.3 搜索算法零分配化 (matchEntry)
- **优化点**：废除 `QString::toUtf8().constData()` 的级联调用。
- **实现**：直接对比 `m_string_pool` 中的原始字节。利用 SoA 的 `m_ext_offsets` 数组实现针对性后缀匹配，跳过所有字符串解析步骤。

## 6. 实现准则与预警【核心】
- **内存安全预警**：在异步排序投影期间，由于 SoA 指针可能随 `vector` 扩容而变化，方案强制要求投影时拷贝字符串内容而非仅拷贝指针。
- **并发同步**：所有从子线程向 UI 线程的回调必须通过 `Qt::QueuedConnection` 投递，确保视图模型操作在主线程执行。
